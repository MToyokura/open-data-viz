# 資産分布データJSONの分割配信計画

## 背景

`data_preparation/output/asset_distribution/asset_distribution.json` は、分類辞書・組み合わせ一覧・全階級値を一つに含み、約30 MBある。ページを開くと全件を取得・JSON解析・検証し、属性を一つ選ぶだけでも全値をブラウザーに載せるため、初期表示と操作が重い。

ローカルではルートの `npm run serve` が `data_preparation/output/` を静的配信し、本番では `VITE_STORAGE_BASE_URL` 配下の同じディレクトリ構造からデータを読む。この配信方式は維持し、ページが必要とする階級値だけを取得できる小さなJSON群を生成する。

## 目的と対象

- 初期表示で全階級値をダウンロード・解析しない。
- 初期選択の系列と、ユーザーが選んだ比較系列に必要な値だけ取得する。
- 既存の秘匿・欠損値の扱い、比較可否判定、公式分類辞書を維持する。
- 生成物を既存のローカル静的サーバーおよび本番の静的データ配置で配信可能にする。

年次切替やAPIのブラウザー直接呼び出し、データのページ表示時更新は対象外。

## 分割方式

`asset_distribution.json` を配信用の必須ファイルとして使う方式から、次の構成に移行する。

```text
data_preparation/output/asset_distribution/
  manifest.json
  items/
    00000.json
    00001.json
    ...
```

- `manifest.json` は `schema_version`、メタデータ、分類辞書 (`dimensions`)、全組み合わせと公表状態 (`combinations`)、値ファイルの一覧を含む。選択肢や比較可否の判定に必要な情報は初期取得で利用可能にする。
- 値ファイルは、決定的な順序で並べた `combination_id` を固定件数ずつまとめ、その組み合わせの通常階級値 (`items`) を格納する。manifest は各組み合わせから値ファイルへの対応を持つ。
- 1組み合わせの全階級値を同じチャンクに置き、選択系列の取得先を一意にする。比較時は公表中の系列に対応するチャンクだけを取得し、同じチャンクへの重複リクエストを避ける。
- 初期チャンク件数は128組み合わせを目安とし、実データで圧縮前サイズを計測して調整する。チャンクは概ね256 KiB〜1 MiBを目標とする。組み合わせ数や値の注記量が変化しても過大ファイルを作らないよう、必要なら目標バイト数による分割を採用する。1組み合わせが目標を超える場合も、その組み合わせを欠落・分割せず単独チャンクにする。
- チャンクID・出力順は入力や実行環境に左右されない決定的なものとし、manifest とチャンクの内容が対応していることを生成時に検証する。

既存の30 MB単一JSONは、移行後のページでは読み込まない。再生成時に残骸が配信されないよう、出力の入れ替え時に旧ファイルを削除する。ほかの利用者が単一JSONを参照していないことをリポジトリ内で確認し、必要なら移行期間だけ変換用成果物として明示的に残す。

## 実装手順

### 1. サイズと利用箇所を確認

- 既存出力の総バイト数、metadata / dimensions / combinations / items ごとのサイズ、組み合わせ数、1系列あたりの階級数を記録する。
- `asset_distribution.json` の参照箇所をリポジトリ内で洗い出し、利用者と旧形式の扱いを決める。
- 目安チャンク数で仮分割し、最大・中央値サイズと、初期系列・代表的な比較に必要なチャンク数を計測する。

### 2. Rust生成処理を分割出力へ変更

- 整形済みの全値を作る既存検証ロジックは維持し、出力部分を manifest とチャンクに分ける。
- manifest に値ファイルの相対パス、対象 `combination_id`、任意でバイト数を記録し、組み合わせIDからチャンクを引けるようにする。
- 公表組み合わせには通常階級の各値が一度だけ存在し、非公表組み合わせには値を生成しない既存の完全性条件を維持する。全チャンクを再読込し、重複・欠落・参照先不正を検出してから生成成功とする。
- staging ディレクトリに manifest と全チャンクを書き、検証完了後に現在の出力と入れ替える。途中失敗で旧出力の一部だけが残らないようにする。
- 旧単一JSONへの参照がないことを確認後、そのファイルを生成対象から外し、古い出力も置き換え時に除去する。

### 3. フロントエンドの読み込みを遅延化

- 起動時は `manifest.json` のみ取得し、分類軸・選択肢・組み合わせ状態を使って現行のUIを初期化する。
- `findCombination` と選択可否判定は manifest の組み合わせ情報だけを参照し、階級値の取得を待たずに実行する。
- 現在選択中の公表組み合わせに必要なチャンクを取得し、系列値を表示する。比較中は選択中の公表系列に必要なチャンクを取得する。
- チャンク単位のPromise/データキャッシュを設け、複数系列が同じチャンクを使う場合の重複取得を防ぐ。取得済みチャンクは選択を戻した際に再利用する。
- 表示条件の変更が連続した場合、古い取得結果で新しい選択結果を上書きしないよう、選択世代の確認などで表示を制御する。
- manifest・チャンクそれぞれのHTTPエラー、JSON解析エラー、schema/version不一致、未登録チャンク、系列値の欠落を既存の日本語エラー表示に接続する。取得中は初期表示と比較系列の状態を区別して示す。
- 大きな `data.items` 全体を保持する現在の検証処理を廃し、manifest 検証と読み込んだチャンクの局所検証に分ける。チャンク検証時は系列・階級の重複、状態と値の不整合、manifest にない組み合わせを検出する。

### 4. 配信パス・説明を更新

- データ取得URLを `/asset_distribution/manifest.json` とチャンク相対パスに変更する。
- ローカル `npm run serve` と本番の `VITE_STORAGE_BASE_URL` で、manifest と配下のJSONが同一のディレクトリ構造で取得できるようにする。
- データ準備READMEと関連する計画・出力説明を更新し、生成物の構成と再生成方法を記載する。
- 公開前に本番静的データ配置の更新対象を明確にし、古い単一JSONを使うページやキャッシュが残らないようにする。

## 検証項目

- 生成 manifest の全組み合わせが既存出力と一致し、各 `published` 組み合わせに通常階級値が全件一度ずつあり、`not_published` には値がない。
- 全チャンクの再結合結果が従来の `items` 配列と同じレコード・状態・注記を持つ。
- 生成を繰り返してもチャンク名・内容・manifest の対応が安定し、失敗時に前の完全な出力が維持される。
- 初期ロードのネットワーク要求にチャンクが含まれず、初期選択に必要なチャンクだけを後続取得する。
- 単一条件の切替、比較の開始・解除、同一チャンクを共有する比較、非公表系列を含む比較で既存の操作・表示結果が保たれる。
- 切替を素早く連続操作しても、画面に現在の選択条件に対応する系列だけが表示される。
- 取得失敗、壊れたJSON、manifestと不一致のチャンク、値欠落・重複が利用者向けのエラーになる。
- 旧単一ファイル全体を取得しないこと、初期転送量と代表操作の追加転送量、チャンク数・サイズを記録し、現状より初期転送量が十分小さくなったことを確認する。
- ローカル静的配信と本番静的データ置き場の両方で、ファイルパスとCORSを含む取得が成立する。

## 完了条件

- 初期表示はmanifestのみを取得し、現在の系列または比較系列に必要な値チャンクだけを遅延取得する。
- 旧単一JSONの全内容を配信・解析する経路がページからなくなり、操作結果とデータ状態の意味が移行前と一致する。
- 出力生成時に値の網羅性・一意性・参照整合性を検証し、ローカルおよび本番の静的配置で動作する。
- 初期転送量と代表操作の転送量を計測し、結果をREADMEまたはinspection記録に残す。
