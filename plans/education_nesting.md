# 教育区分の階層表示計画：労働力調査・純資産分布

## 目的

労働力調査の教育区分と、全国家計構造調査の世帯主の学歴区分を、それぞれのe-Stat分類と並びから読み取れるまとまりに沿って表示する。比較画面・条件選択・系列名で階層が一貫して伝わるようにする。

この計画では公式の分類名や値コードを書き換えず、公式データ上の関係と画面上の見せ方を分けて扱う。

## 対象A：労働力調査の教育区分

### 現状と確認済みの点

- 対象は e-Stat 統計表ID `0003006608`（年次表 1-5-1）。画面上の教育軸は11区分。
- APIメタデータの並びは `00 総数`、`01 うち在学中`、`02 小学・中学・高校`、`03 短大・高専`、`04 大学・大学院`、`05 うち卒業`、`06 小学・中学・高校・旧中`、`07 短大・高専`、`08 大学・大学院`、`09 大学`、`10 大学院`。
- e-Statの年次表と統計局の表項目資料でも、総数に続いて「うち在学中」の区分群と「うち卒業」の区分群が掲載されている。
- `@level` は `00` が1、`01` と `05` が2、それ以外が3。`@parentCode` は `03`・`04` に `02`、`06`〜`10` に `05` が設定されている。`02` に親コードはなく、`03`・`04` の親コードと区分名・表上の並びだけから想定される「在学中」グループとの対応は自明でない。
- 現在の画面は、重複する名称を系列名・比較選択肢で区別するため、`03`・`04` に「在学中 >」、`07`・`08` に「卒業 >」を付けている。条件のドロップダウンは公式名のまま。その他の区分は裸の名称で、画面間で階層表示が揃っていない。

- APIメタデータ標本: [`data_preparation/inspections/workers_by_age_employment_type_education_sex/samples/meta_info.json`](../data_preparation/inspections/workers_by_age_employment_type_education_sex/samples/meta_info.json)

### 方針

### 1. 公式メタデータと表示用階層を分離する

APIから得た各区分の `code`、公式 `name`、順序、`level`、`parentCode` は原形のまま保持する。親コードを上書きしたり、公式名称に説明語を混ぜたりしない。

表示用には、区分コードを参照する独立した階層定義を持つ。現時点の候補は次の形とする。

```text
総数 [00]
├─ うち在学中 [01]
│  ├─ 小学・中学・高校 [02]
│  ├─ 短大・高専 [03]
│  └─ 大学・大学院 [04]
└─ うち卒業 [05]
   ├─ 小学・中学・高校・旧中 [06]
   ├─ 短大・高専 [07]
   ├─ 大学・大学院 [08]
   ├─ 大学 [09]
   └─ 大学院 [10]
```

この構造は「画面でまとまりを示すための階層」であり、APIの `parentCode` を再解釈した値として保存しない。特に在学中側 `02`〜`04` の関係は、公式表・API仕様の照合結果を記録してから確定する。

### 2. 表示階層と比較可否を別々に定義する

階層上で親子に見えることだけを理由に、親と子の同時比較を禁止または許可しない。比較対象として適切かは、区分の意味と公式表の注記を確認して別途定義する。

「総数」「うち在学中」「うち卒業」は重複する集計範囲を持ち得るため、比較集合や一括選択に含める場合は、内訳区分との混在をどう扱うかを明示する。値の合計が一致することを前提にしない。

### データ確認の手順

### A. e-Stat APIメタデータを確認する

1. 保存済み `data_preparation/inspections/workers_by_age_employment_type_education_sex/samples/meta_info.json` の `CLASS_OBJ` から `cat04` を抽出する。
2. `@code`、`@name`、`@level`、`@parentCode`、配列順を一覧化し、公式表で見える項目順と照合する。
3. e-Stat APIの `getMetaInfo` を再取得し、現行応答でも同じか確認する。取得日時と元応答を保存する。
4. `@parentCode` がない項目は、直前項目から親を推測してAPIメタデータに書き戻さない。

### B. 公式の表・説明資料で意味を確認する

1. e-Stat 年次表 `0003006608` の教育項目選択画面と公式Excelを開き、インデント、見出し、注記、表頭の構造を確認する。
2. 同じ系列の四半期表 `0003006361` と統計局の労働力調査詳細集計の表項目資料を照合する。
3. 「在学中」「卒業」が集計対象の状態を示す親区分なのか、表示上の見出しなのか、また `小学・中学・高校` がどの範囲を表すのかを公式資料の定義で確定する。
4. APIの `03`・`04` の `parentCode=02` と、表のグループ配置が食い違う場合は、両方を記録する。根拠が見つかるまで、APIの親子関係と画面用のグループ構成を同一視しない。
5. 調査票・用語解説に卒業学校や在学状況の定義があれば参照し、画面用補足文の根拠としてリンクを記録する。

### C. 数値を使って集計関係を確認する

1. 同一年・同じ年齢・雇用形態・性別の条件で、`00`〜`10` の値を取得する。
2. `総数`、`うち在学中`、`うち卒業`、各学校区分の値の関係を複数年で確認する。
3. 内訳合計と親区分が一致しない場合は、丸め、欠損、秘匿、対象外区分、区分の重複を確認する。値から親子関係を逆算して決めない。
4. 調査定義や公表値から包含・重複を確定できない関係は「未確認」として残し、比較モードで相互排他的な選択肢として扱わない。

### D. 根拠をリポジトリに残す

- 確認した公式資料のURL、表番号、確認日を `data_preparation/inspections/workers_by_age_employment_type_education_sex/README.md` に追記する。
- API `parentCode` と画面表示用階層が異なる箇所は、コード単位で説明する。
- メタデータ再取得で分類が変わった場合に検知できるよう、確認対象のコード・名前・階層関係を検証対象にする。

### 推奨するアプリ内データ表現

フラットな区分辞書と、コードを参照する表示階層を併存させる。

```js
{
  categories: [
    { code: "00", label: "総数", order: 0, level: 1, api_parent_code: null },
    // API由来の11区分。公式名とAPI関係を保持する。
  ],
  display_hierarchy: [
    { code: "00", children: [
      { code: "01", children: ["02", "03", "04"] },
      { code: "05", children: ["06", "07", "08", "09", "10"] }
    ] }
  ]
}
```

- 実際の実装形式は既存の `options.dimensions.education` を踏まえて決める。
- 表示階層は全コードを一度ずつ参照することを検証する。未知コード、重複コード、未配置コードをエラーとして扱う。
- 階層の各項目はカテゴリコードを参照し、名前やデータ値を複製しない。
- APIの親コードは `api_parent_code` 等として別に保持し、表示用親との違いを失わない。
- 親区分も実データの選択肢なので、単なる見出しにせず、選択可能な項目であることが分かる表現にする。
- `display_hierarchy` と比較集合・比較制約は独立したデータとして管理する。

### UI変更の手順

1. 比較モードの教育区分を、親区分を含む階層リストとして表示する。親の「うち在学中」「うち卒業」も選択可能にする。
2. 繰り返し出てくる「短大・高専」「大学・大学院」には、親の文脈を付けて区別する。表示例は「在学中 > 短大・高専」「卒業 > 短大・高専」。
3. 通常の条件選択と選択済み系列の名称にも同じ表示用ラベルを使い、モードによって意味が変わらないようにする。
4. 系列名・グラフ凡例では、階層が読めるラベルを使う。省スペース表示をする場合も、ツールチップや詳細ラベルで親区分が分かるようにする。
5. 必要なら「総数」「うち在学中」「うち卒業」は集計範囲の見出し・再掲区分だと説明する。特に合計できる／できない関係を未確認のまま断定しない。
6. 画面幅が狭い場合も階層差が文字だけで分かるよう、字下げに加えて接頭ラベルまたは別の見出し構造を用いる。

### 確認項目

- 11区分すべてが公式コード・名称の対応を保って表示される。
- 「在学中」と「卒業」の同名カテゴリが、比較欄・系列一覧・グラフ凡例で区別できる。
- 公式名をデータ値や出典情報に使う箇所では、画面補足語が混入しない。
- 初期条件、追加モード、比較モード、選択済み一覧で同じ区分の表示が一貫する。
- APIメタデータ上の `parentCode` と表示上のグループの違いが説明され、誤って上書きされない。
- 親区分と内訳の同時比較をどう扱うかが仕様化され、未確認ならUIで誤解を招く組合せとして推奨しない。
- 調査結果をもとに、分類のコード順・名前・階層が変わった場合の検証方法を用意する。

### 完了条件

1. 公式表・APIメタデータ・値の照合結果と、在学中側の親子関係に関する不一致または解釈がREADMEに記録されている。
2. 公式の分類名を保持したまま、アプリ内に検証可能な表示用階層が定義されている。
3. 選択欄・比較欄・系列名で階層表示が一貫し、同名カテゴリの親が分かる。
4. 親区分と内訳の比較ルールが明記され、表示階層と比較ルールが混同されていない。
5. データ整合性検証と画面確認で、全11区分が欠落・重複なく扱われる。

## 対象B：日本の純資産分布の学歴区分

### 現状と確認済みの点

- 対象は e-Stat 統計表ID `0004056120`（令和6年全国家計構造調査、表7-131-1-1）。学歴軸 `cat02` は「世帯主の学歴6区分」。
- APIメタデータには `0 平均`、`1 在学中`、`2 卒業`、`21 小学校・中学校`、`22 高校程度`、`23 短大程度以上` の6区分がある。
- `0`、`1`、`2` は `@level=1`。`21`〜`23` は `@level=2` で `@parentCode=2`。したがって「卒業」は卒業者全体の親区分で、後ろの3つはその内訳。
- 学歴の「平均」は、既存の調査記録・生成処理では学歴を限定しない全体区分（`total_code=0`）として扱っている。表章項目は「世帯数分布」で、この区分の値も世帯数を表す。公式名「平均」を保持し、全体区分の対象範囲を公式資料で確認する。
- 生成処理は比較集合として `[1, 2]`（在学中・卒業）と `[21, 22, 23]`（卒業者の内訳）を別々に定義している。親区分 `2` と子区分 `21`〜`23` を同じ比較集合に混ぜない。
- 画面では選択肢に `卒業（全体）`、子区分に `卒業者の内訳：…`、比較集合に「在学中・卒業者全体」「卒業者の学歴内訳」と補足している。公式分類名はデータ側で保持する。

### 参照資料

- [e-Stat 年次表 7-131-1-1（統計表ID `0004056120`）](https://www.e-stat.go.jp/dbview?sid=0004056120)
- [全国家計構造調査の公式利用上の注意](https://www.stat.go.jp/data/zenkokukakei/2024/pdf/riyou2024.pdf)
- [公式Excel 表7-131-1](https://www.e-stat.go.jp/stat-search/file-download?statInfId=000040490406&fileKind=0)
- APIメタデータ標本: [`data_preparation/inspections/asset_distribution/samples/meta_info.json`](../data_preparation/inspections/asset_distribution/samples/meta_info.json)
- 分類確認・比較集合の根拠: [`data_preparation/inspections/asset_distribution/README.md`](../data_preparation/inspections/asset_distribution/README.md)

### データ確認の手順

1. 保存済み `meta_info.json` と現行 e-Stat `getMetaInfo` の `cat02` を照合し、6区分のコード・公式名・順序・`@level`・`@parentCode` を記録する。
2. e-Statの選択画面と公式Excelで、`卒業` が総卒業者を示す親区分で、21〜23がその内訳として表示されることを確認する。
3. 全件 `getStatsData` の組合せを確認し、他の属性条件が同じ `cat02=2` と `cat02=21`〜`23` がそれぞれ公表されることを確かめる。
4. 同一条件で親区分と内訳の値を複数の代表条件について照合する。丸め差や欠損を含む可能性があるため、内訳の単純合計が親の値と常に一致するとは仮定しない。
5. 学歴の `平均` が示す全体区分の対象範囲を公式資料で確認し、根拠を記録する。他の学歴区分と同じく値は世帯数として扱い、在学中・卒業の単純合計との一致は仮定しない。表示階層では独立した選択肢とし、比較集合は状態別 `[1, 2]` と卒業内訳別 `[21, 22, 23]` に限定する方針を、全体区分の意味とは分けて記録する。
6. 公表区分や親コードが更新された場合に検知できるよう、コード・名称・親子関係・比較集合の期待値を生成時の検証に含める。

### 推奨するアプリ内データ表現

分類のフラットな辞書、画面用の階層、比較集合を別々に持つ。`平均` は階層グループから独立した選択肢として扱い、既存の全体区分の指定（`total_code=0`）を保持する。

```js
{
  categories: [
    // APIのコード・公式名・順序を保持する6区分
  ],
  display_hierarchy: {
    standalone_codes: ["0", "1"],
    groups: [
      { code: "2", children: ["21", "22", "23"] }
    ]
  },
  comparison_sets: [
    { id: "education-status", category_codes: ["1", "2"] },
    { id: "graduated-subgroups", category_codes: ["21", "22", "23"] }
  ]
}
```

- `categories` の公式名を画面向け文言で上書きしない。APIの `@level` と `@parentCode` は取得・変換時に検証し、表示階層はコード参照で定義する。
- 画面用階層は全6コードを漏れなく一度だけ参照する。未知コード、重複、未配置を検出する。
- 表示上のグループと比較集合は別の役割を持つ。比較集合は親子の重複を避けるために分けて保持する。
- 比較集合の名前も、公式の分類名ではなく操作内容を説明するUIラベルとして管理し、公式名と混同させない。

### UI確認項目

1. 通常の選択欄で `卒業` が卒業者全体を示すと分かり、子3区分がその内訳として読める。
2. 比較集合の切替時に、親区分2つの比較と卒業内訳3区分の比較が別のまとまりだと分かる。
3. 凡例・選択済み系列・比較チェック欄でも同じ表示用ラベルを使う。
4. 公式名は出典・データ詳細で確認でき、補足語が公式名として誤認されない。
5. 子区分が利用できない組合せがある場合も、親子関係と公表可能性を混同しない。利用可否は組合せデータで判定する。
6. 学歴の `平均` を選択した系列も世帯数として表示し、学歴を限定しない全体区分であることが分かる説明を、公式資料で確認した対象範囲に基づいて付ける。

### 完了条件

- `cat02` の全6コードが欠落・重複なく表示される。
- `卒業` とその3内訳、および学歴を限定しない全体区分 `平均` の違いが選択欄と比較欄で伝わり、いずれの値も世帯数として扱われる。
- 比較集合 `[1, 2]` と `[21, 22, 23]` が独立して保たれ、親と子が同じ比較集合に混在しない。
- 元データの公式名称・コード・値を変更せず、表示用階層だけを追加できる。
- メタデータ検証と画面確認により、区分更新時の不整合を検知できる。
