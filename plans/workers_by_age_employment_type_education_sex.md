# 雇用者数ページ再実装計画

## 目的

旧ページ「年齢階級，教育，雇用形態別雇用者数(2002年～)」を、現在の SvelteKit / Svelte 5 フロントエンドと Rust データ準備パイプラインに再実装する。年齢階級・就業状態・教育・性別を選び、系列をグラフに追加して年次推移を比較できるようにする。

## 現行構成との対応

- フロントエンドは `frontend/src/routes/` 以下にページを置き、統計ごとの取得処理・定数・型をページディレクトリ内にまとめている。小売価格ページの `commodity_prices/` を構成の参考にする。
- グラフは Apache ECharts を `LineChart.svelte` で遅延ロードしており、ページ側から ECharts option を渡す。雇用者数では年次の複数系列を比較するため、棒グラフ用の専用コンポーネントを設ける。
- ブラウザーは `VITE_STORAGE_BASE_URL` で指定した静的 JSON 配信先からデータを取得する。Rust の生成物は `data_preparation/output/` 以下に置かれる。
- Rust の e-Stat API 呼び出しは `data_preparation/src/modules/estat_api/` にあり、統計ごとの取得・変換処理は `modules/projects/` に追加する。

## データ仕様の確認

実装前に e-Stat 統計表 ID `0003006608`（旧ページの出典）を現行 API で確認する。

1. 統計表が引き続き利用できるか、表の改定・後継表の有無、対象期間と更新状況を確認する。
2. メタデータから年齢階級、雇用形態、教育、性別、時間軸の分類コード・表示名・順序を確定する。旧ページの「就業状態」フィルターと表の「雇用形態」分類の対応も確認する。
3. データ値の単位、年次のコード形式、欠損・秘匿・該当なし等の表現を確認する。数値に変換できない値をゼロとして扱わない。
4. 有効な分類組み合わせ、データ量、API の取得上限・ページング要否を確認し、取得粒度を決める。

分類コードや表の仕様が旧ページと変わっている場合は、確認結果に合わせて選択肢と表示名を定義する。旧ページの選択肢を無条件にコードとして流用しない。

### inspections での API 応答形式の調査

本番の取得・変換処理を実装する前に、`data_preparation/inspections/workers_by_age_employment_type_education_sex/` で実際の e-Stat API 応答を取得し、想定するデータ構造で扱えるかを確認する。

1. 再実行できる調査用コマンドまたはスクリプトを用意し、`getMetaInfo` と `getStatsData` の応答を保存する。表 ID、取得日時、エンドポイント、絞り込み条件、`startPosition` / `limit` を記録する。アプリケーション ID は環境変数から読み、応答内のリクエスト情報を含め、保存物やログに残さない。
2. メタデータの `CLASS_INF.CLASS_OBJ` と `CLASS`、統計データの `DATA_INF.VALUE`、`NOTE`、`RESULT`、`RESULT_INF` 等について、実際の階層・キー・型・必須／任意項目を調べる。単一件と複数件でオブジェクト／配列が変わるか、データなしで項目が省略されるかも確認し、既存の小売価格用 Rust 型をそのまま流用できるとは仮定しない。
3. 各レコードの分類属性（`@tab`、`@cat01` 等）、地域、時間、単位、値（`$`）、注記の対応を整理する。4条件以外の次元がある場合は、固定する分類コードと根拠を記録し、4条件と年で値を一意に識別できることを確認する。年次以外の時間区分や複数の指標を混在させない。
4. 通常の複数件、絞り込みによる単一件、データなし、欠損・特殊値を含む条件を調べる。小さな `limit` で複数ページを取得し、件数・次ページ情報と境界のレコードを照合する。観測できなかったケースは未確認として明記し、仕様に基づく想定と実測結果を分ける。
5. `README.md` に再実行手順、応答サンプルの所在、想定形式と実際の形式の比較、差異、採用する型・正規化方法、未確認事項をまとめる。最小限の応答サンプルと確認レポートを残し、`data_preparation/inspections/README.md` のテーマ一覧からリンクする。

調査結果を根拠に Rust の入力型とフロントエンド向け JSON 契約を確定する。未確認事項が変換の正しさに関わる場合は追加調査し、確認済みの応答サンプルを固定入力のテストに利用する。

## データ準備（Rust）

対象ディレクトリ案: `data_preparation/src/modules/projects/workers_by_age_employment_type_education_sex/`

1. `modules/projects/mod.rs` と CLI に `workers-by-age-employment-type-education-sex` コマンドを追加する。
2. 統計表 ID、出力先、分類コード等を統計専用モジュールにまとめる。
3. e-Stat メタデータと統計データを取得し、既存の commodity prices 処理に倣ってメタデータ・生データ・変換済みデータを保存する。取得済みデータの再利用方法を決め、再取得が必要な場合に更新できるようにする。
4. API 件数上限を超える場合は既存の `start_position` / `limit` を使って漏れなく取得する。ページング境界で重複・欠落がないことを検証する。
5. フロントエンド向けの選択肢 JSON と、データが存在するすべての分類組み合わせごとの時系列 JSON を生成する。出力形式案:

   ```text
   output/workers_by_age_employment_type_education_sex/
     meta_data/options.json
     transformed_data/{年齢コード}{雇用形態コード}{教育コード}{性別コード}.json
   ```

   時系列 JSON は分類コード・分類名、単位、年と値の配列を含める。ファイル名の連結が曖昧にならないよう、コード長を固定するか区切り文字を使う。欠損値は元データの意味を保って表現する。

   `options.json` には各分類の選択肢に加え、データが存在する系列の一覧（4条件のコードと時系列 JSON の相対パス）を含める。元データにレコードがあり、値がすべて欠損の系列も一覧と出力に含める。一覧にない組み合わせはデータなしと判定し、一覧にあるファイルの取得失敗とは区別する。一覧と時系列 JSON は同じ取得データから生成し、一覧に記載したファイルがすべて存在することを確認する。
6. 出典表 ID、取得日時、対象期間など再現に必要な情報をメタデータまたは README に記録する。

## フロントエンド

対象ディレクトリ案: `frontend/src/routes/workers_by_age_employment_type_education_sex/`

1. `+page.svelte` を追加し、ページタイトル・説明・出典欄を表示する。
2. `utils/` に選択肢 JSON と系列データの fetch 関数を置き、`constants/` に配信 URL、`types.js`（または既存の型定義方式）にデータ構造を定義する。
3. 年齢階級、就業状態／雇用形態、教育、性別の選択 UI を作る。選択肢と初期値は生成済みメタデータから構成し、固定の分類コードに依存させない。
4. 「追加」で選択中の系列を取得してグラフに加える。4条件のコードを系列の識別子とし、取得中・追加済みの同一系列の重複追加を抑止する。追加操作時に条件と表示順を確定し、応答の到着順によらず追加操作順に一覧・凡例・グラフを並べる。取得中の項目も一覧表示し、個別削除と全消去を提供する。削除時は該当リクエストを、全消去時はそれ以前のすべてのリクエストを無効化し、遅れて届いた成功・失敗の応答で系列やエラー表示が復活しないようにする。同じ条件を再追加した場合も、古いリクエストの応答を反映しない。
5. ECharts の棒グラフで年次推移を比較する。表示する全系列の年の和集合を昇順で共通軸にし、各系列の値を年をキーに配置する。系列に存在しない年と元データの欠損値は、ゼロに変換せず棒を描画しない。ツールチップ等では元データの欠損理由と系列に年が存在しないことを区別する。旧ページの縦／横向き切替を引き継ぎ、狭い画面でもラベルと凡例を読めるようにする。リサイズはコンテナの `ResizeObserver` で扱う。
6. データ未存在、取得失敗、選択肢ロード中、系列取得中を区別して表示する。選択肢 JSON の取得・検証が完了するまでは追加操作を無効にする。選択した組み合わせが `options.json` の系列一覧にない場合に「該当するデータがありません」と表示する。一覧にある時系列 JSON や選択肢 JSON の404、その他の通信失敗、JSONの解析・検証失敗は再試行可能なエラーとして扱う。値がすべて欠損の系列は「データなし」と混同せず、値を表示できない理由を示す。
7. トップページの「今あるもの」にページリンクを追加する。
8. 出典欄に e-Stat 表 ID・統計名・表題・単位・対象期間・労働力調査の説明へのリンクを載せる。旧ページの説明は、データ確認後に現行の表情報へ更新する。

## 検証項目

- inspections の実測応答が採用する入力型で読み取れ、分類・時間・値・注記を失わず解釈できることを確認する。単一件・複数件・データなし・ページングについて、実測したケースと未確認のケースを記録する。
- Rust の変換処理で、コード・ラベル・年次・値・単位が元データと一致することを小さな固定入力で確認する。
- 取得件数と変換後件数を照合し、年次や分類の欠落、重複、欠損のゼロ化がないことを確認する。
- フロントエンドで選択肢の読込、系列追加、複数系列の比較、個別削除、全消去、データなし、通信失敗を確認する。
- 系列一覧と出力ファイルが一致し、一覧にない組み合わせはデータなし、一覧にあるファイルの404や選択肢 JSON の取得失敗はエラーになることを確認する。全値欠損の系列も一覧に残り、欠損理由を表示できることを確認する。
- 対象期間が異なり、途中の年が欠けた2系列を使い、年の和集合が昇順の共通軸になり、値が正しい年に配置されることを縦・横の両方向で確認する。存在しない年や欠損値の棒がゼロとして描画されないことも確認する。
- 応答順を逆転させた連続追加でも追加操作順を保つこと、取得中・追加済みの重複追加を抑止することを確認する。取得中の個別削除・全消去・同条件の再追加後に古い成功・失敗の応答が届いても、削除した系列や古いエラーが復活しないことを確認する。
- 既存の `npm run check`、`npm run test`、Rust のテスト・ビルドにこのページの確認を加え、既存ページに回帰がないことを確認する。
- 静的ビルドとプレビューで `/workers_by_age_employment_type_education_sex` が表示され、`BASE_PATH` と `VITE_ROOT_PATH` が設定された配置でもリンクとデータ取得が機能することを確認する。
