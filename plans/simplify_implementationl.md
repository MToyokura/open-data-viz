# 実装の簡略化計画

## 目的と運用方針

趣味で運営するサイトとして、更新中の停止や表示エラーを許容し、保守するコードと公開手順を減らす。更新に失敗した場合は、以前の状態へ自動復旧せず、原因を直して再生成・再公開する。

- 配信用の成果物は毎回作り直してよい。
- フロントエンドと配信データの同時切り替え、更新中の新旧データの整合性は保証しない。
- 更新前から開いていた画面は、更新後に再読み込みしてもらう。
- 外部 API の応答や公式ワークブックのローカル保存は維持する。配信用データの再生成と、原本の再取得は分ける。
- 統計の解釈と値の正しさを守る検証は維持する。
- エラー時は失敗として終了する。途中の成果物を成功扱いして公開しない。

この文書は実装計画であり、実際の GCS オブジェクトの削除・公開は実装変更とは別の操作として扱う。

## 1. GCS 公開処理の簡略化

### 現状

対象:

- `data_preparation/src/modules/publish_gzip.rs`
- `data_preparation/src/main.rs`
- `data_preparation/src/modules/mod.rs`
- `data_preparation/PUBLISHING.md`

現在は gzip ステージの作成に加えて、既存オブジェクトのバックアップ、CRC32C と世代番号の照合、メタデータの修復、条件付きアップロード、全件再ダウンロード検証、復旧まで扱っている。公開手順にも manifest の更新順序、古いチャンクの保持、削除許可一覧などがある。

### 削るもの

- 公開前の既存本体・メタデータの全件バックアップと復旧手順。
- generation / metageneration による競合防止。
- 既存オブジェクトに応じた「変更なし・メタデータ修復・再アップロード」の分岐。
- 全ファイルの再ダウンロード、バイト列比較、再展開検証。
- prefix ごとの既存キャッシュ方針の調査と継承。
- チャンク検証後に manifest を更新する特別な公開手順。
- 旧チャンクの継続利用を前提にした保持期間と削除許可一覧。

### 実装手順

1. 公開処理を小さなスクリプトにまとめる。配置先の例は `data_preparation/scripts/publish.sh`。
2. `PUBLISHING.md` の公開対象一覧を基に、ブラウザーが使うファイルだけを一時ディレクトリへ集める。API 原本、取得メタデータ、監査用ファイルは混ぜない。
3. 一時ディレクトリ内の JSON / GeoJSON を gzip 圧縮する。URL とファイル名は維持する。
4. Content-Type、Content-Encoding、Cache-Control を公開時に明示する。キャッシュ方針は共通の短い有効期間など、単純な設定に統一する。gzip 配信に必要な設定は維持する。
5. 公開対象の prefix ごとにアップロードする。既存ファイルの状態に応じた独自の修復処理は設けない。
6. 不要ファイルの削除が必要なら、公開専用の prefix に限定して同期時に削除する。バケット全体や原本保存先を削除対象にしない。全削除してからの再アップロードは必須にしない。
7. スクリプトは必須入力・公開先・公開ファイルの存在を最低限確認し、コマンドの失敗時に終了する。
8. `gzip-stage` / `gzip-reconcile` の利用箇所を置き換え、不要になった Rust モジュールと CLI 分岐を削除する。依存関係は利用箇所を確認して、不要なものだけ削除する。
9. `PUBLISHING.md` を、認証・公開コマンド・代表ページの確認・失敗時の再実行という短い手順に書き直す。

### 完了条件と受け入れる制約

- 一つの公開コマンドで、対象ファイルの収集・圧縮・アップロードができる。
- 独自の GCS 修復・ロールバック処理がなくなる。
- 初回公開でも既存データのバックアップを要求しない。
- 更新途中や失敗後に、一部ページが使えない状態になり得る。再公開で解消する。
- gzip 配信と必要な HTTP メタデータは維持する。

## 2. データ生成時の切り替え・ロールバックの削除

### 現状

対象:

- `data_preparation/src/modules/projects/workers_by_age_employment_type_education_sex/pipeline.rs`
- `data_preparation/src/modules/projects/asset_distribution.rs`

取得・変換結果を `.staging` に作成し、既存データを `.previous` に退避して入れ替える。途中の操作が失敗した場合は以前のディレクトリへ戻す。

### 実装手順

1. 取得結果と配信用成果物について、削除・再作成するディレクトリの範囲を明確にする。
2. 取得処理は、その取得先を空にして直接書き込む方式へ変更する。失敗した取得結果は不完全なものとして扱う。
3. 変換処理は、取得済み原本を残し、配信用成果物だけを空にして直接書き込む方式へ変更する。
4. `.staging` / `.previous` の作成・退避・復元・清掃と、純資産分布の `replace_distribution_bundle` / `restore_distribution_backup` を削除する。
5. 純資産分布の出力検証は、実際の生成先に対して実行できるようにする。検証の内容自体はこの段階では維持する。
6. `--transform-only` は残す。不完全な取得結果や取得ページの欠落を検出する検証も残す。
7. README に「生成失敗後は再実行する」「成功した生成結果だけを公開する」と記載する。

### 完了条件と受け入れる制約

- ディレクトリ入れ替えと自動復旧の分岐がなくなる。
- 変換だけの再実行では原本が消えない。
- 再生成時に以前の不要な配信ファイルが残らない。
- 失敗時にローカルの生成先が不完全になることを許容する。
- ローカル生成の失敗だけで、公開済みデータは変更されない。

## 3. 野菜データの既存成果物再利用判定の削除

### 現状

対象:

- `data_preparation/src/modules/projects/vegetable_production_relay/generation.rs`
- 必要に応じて同ディレクトリの `aggregation.rs` / `product_index.rs`

既存の品目別出力について、品目・状態・年数・マッピングハッシュ・正規化入力ハッシュを照合し、一致すれば集計の再生成を省略している。既存ファイルが不正な場合は再生成前に停止する分岐もある。

### 実装手順

1. `generate_product_data` の既存品目ファイルの読み込み・検証・再利用判定を削除する。
2. 取得済み原本と確定済みマッピングから、正規化・集計・summary・詳細・品目索引を毎回生成する。
3. 集計処理に既存ファイルの存在で書き込みを拒否する前提があれば、生成先の初期化と合わせて調整する。
4. 配信用成果物を初期化する際は、同じ出力ディレクトリ内の別用途のファイルまで消さないよう対象を限定する。
5. ハッシュは用途ごとに扱う。再生成を省略するためだけの計算・変数は削除し、原本・分類対応・出典の検証で必要なものは維持する。
6. README の「既存成果物を維持する」などの説明を、毎回再生成する動作に合わせる。

### 完了条件と受け入れる制約

- 既存の配信用ファイルが壊れていても、それを読まずに再生成できる。
- 既存成果物のハッシュ一致によるスキップがなくなる。
- 原本のキャッシュと公式資料との対応確認は維持する。
- 毎回の正規化・集計にかかる時間の増加を許容する。

## 4. フロントエンドの形式検証を生成側へ集約

### 現状

主な対象:

- `frontend/src/routes/asset_distribution/utils/data.js`
- `data_preparation/src/modules/projects/asset_distribution.rs` の出力検証

ブラウザー側で分類コードの重複、比較集合、表示階級、直積件数、チャンク範囲などを詳しく検証している。自前の生成プログラムにも出力検証があり、責務が重複している。

### 実装手順

1. ブラウザー側の検証を列挙し、生成側で同等の不整合を検出しているか確認する。
2. 生成側の検証が成功した形式をフロントエンドの入力契約とする。不足する検証は生成側に集約する。
3. ブラウザー側は HTTP ステータス、JSON の読み込み、対応する schema version、表示に必要な最低限の存在確認へ縮小する。
4. 重複コード・比較集合・全チャンク範囲などの詳細な検証を削除する。
5. 検証時に構築している `combinationIndexes` などは、検索にも使っているため、検証削除と一緒に無条件で消さない。必要な索引構築を通常の読み込み処理に移すか、既存の検索処理を単純化する。
6. 検証専用のテストは責務の移動に合わせて整理し、組み合わせ検索・表示階級・値の対応を守るテストは維持する。

### 完了条件と受け入れる制約

- 詳細なデータ整合性検証の責務が生成側にまとまる。
- 通信失敗や未対応バージョンは画面でエラーとして扱える。
- 不正データに対するブラウザー側の詳細な診断能力は減る。
- 検証削除によって検索用の索引構築や通常の表示が壊れない。

## 維持する処理

- 欠損値・秘匿値・観測値の区別。欠損や秘匿をゼロで埋めない。
- 単位、年、分類、品目、地域、期間の対応確認。
- API ページの欠落・重複など、取得結果の不完全さの検出。
- 原本・マッピング・公式資料の対応確認に必要な検証。
- 認証情報の除去と、公開するファイルの限定。
- API 負荷を抑える待機や、原本の再利用。
- UI の非同期処理で古いリクエストが現在の選択を上書きしない制御。
- 大きなデータのチャンク分割と gzip 圧縮。転送量・表示速度のための仕組みとして維持する。

GitHub Pages の workflow は現状でも比較的単純なので、まずは変更対象にしない。フロントエンドのキャッシュやリクエスト共有も、操作性や通信量への影響を見ずに一括削除しない。

## 実装順序と確認

1. 公開スクリプトと短い公開手順を作り、Rust の公開専用処理を削除する。
2. 雇用者数、純資産分布の順で生成時のロールバックを削除する。
3. 野菜データの既存成果物再利用判定を削除する。
4. 生成側の検証範囲を確認してから、ブラウザー側の詳細検証を削減する。

各段階は独立した変更として扱い、データ形式を変えずに進める。公開処理を変更する段階で、統計の集計ロジックやチャンク形式まで同時に変更しない。

実装時の確認項目:

- 取得済み原本から変換でき、変更前後で統計値・分類・参照先が一致する。
- 同じ生成処理を再実行でき、不要な成果物が残らない。
- 生成途中で失敗しても成功扱いにならず、次の実行で作り直せる。
- 公開用ディレクトリに原本・監査ファイル・認証情報が含まれない。
- 公開時の圧縮形式と HTTP メタデータが対応している。
- 公開を行う場合は、各ページの初期表示と選択変更を確認する。

全データのネットワーク再取得や本番公開を、コード変更の確認のために毎回行う必要はない。取得済み原本とローカル成果物を使って確認し、実際の公開は必要なタイミングで行う。
